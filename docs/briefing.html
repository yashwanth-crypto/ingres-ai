INGRES: what we built, and how to talk about it

A groundwater assistant for Punjab whose whole design is arranged around one problem — not answering, but never answering wrongly.

The 30-second version

Every one of us should be able to say this without notes.

Ask a plain-English question about Punjab groundwater and get an answer built from real CGWB monitoring data — with a chart, a map, and a citation for every figure. The hard part isn't generating an answer. It's never generating a wrong one.

If you only remember one thing: this is a verification system that happens to have a chat box on it. Most projects at a hackathon will be a language model with a prompt. Ours is a pipeline where the language model is deliberately kept away from anything that matters.

The one idea

Everything else in the project follows from this.

A language model asked about groundwater will produce a fluent, confident, entirely invented figure. So we do three things:

Ask the database, not the model. Numbers come from SQL over real readings — each with a station name and a date attached. The model writes prose around figures it was handed. It never supplies them.

Verify with code, not with another model. We do have a model reviewing the output, but it is advisory only — because during testing it approved an answer citing Kot Shamir, a Bathinda station, as the source for a Ludhiana figure. Eight plain-Python checks run first and can block an answer. They cannot hallucinate, because they don't generate anything.

Two sources, chosen deliberately. The database knows how much water there is. It knows nothing about quality. Quality, causes and methodology come from CGWB's report via semantic search — but numeric questions never go there, because retrieving prose about a figure loses the station and the date that make it checkable.

How it actually works

Five agents. Three of them involve no model at all — that's the part worth saying out loud.

1Understand the questionTurns it into structured intent. Also resolves "and what about Moga?" against the conversation.model
2Fetch the dataMaps intent to SQL, or to a search over the CGWB report.plain code
3Do the mathsProjects the water table forward. numpy, not the model.plain code
4Write the proseThe only place the model touches the answer.model
5Check every figureEight checks over citations, numbers, districts, years, units. Blocking.plain code

The chart, the map and the citations are built from the data, not from anything the model said — because the model was observed leaving both "needs a chart" flags false on questions that obviously wanted one.

The demo, in order

Roughly 40 seconds of answers, four to five minutes with talking. Order matters — each question adds one new capability.

One question at a time. Nothing queues requests in front of the model. Two at once collapse it — a question that answers in 13 seconds took 183 with a second in flight. If a judge reaches for the keyboard mid-answer, let the current one finish. This is the most likely way the demo goes wrong.

While each answer works, a list of steps builds on screen — "Retrieved — 22 stations reporting on 2024-01-01", "Checking every figure — 7 checks over 7 figures". Read a line aloud as it appears. That list is the pipeline, and it's the most convincing thing on the screen.

  1. What's the groundwater status in Bathinda? · 3s

    Show: the trend chart, drawn as a cross-section with ground filled above the water line.

    Say: the Y axis is inverted on purpose — a falling line means a falling water table, which is what people expect.

  2. Which districts in Punjab are over-exploited? · 5s

    Show: the map, and the footnote underneath it.

    Say: "Malerkotla is categorised but not shown — it has no monitoring stations." It tells you what's missing instead of quietly showing fewer pins.

  3. Which district has the worst water table? · 4s

    Show: ranked bars, worst first, the answer at full strength and the rest dimmed.

    Say: a superlative names no district, so this has to rank all of them. An earlier version answered it with one of the shallowest — deep water is a low water level, and the wording fooled it.

  4. How many years until Ludhiana hits critical depth? · 8s

    Show: the projection, dashed into a shaded future, landing on a marked crossing of the 30 m line.

    Say: CGWB publishes no "critical depth" — its categories measure extraction against recharge, not metres. 30 m is a pumping limit we state openly, and the answer says so itself. The maths is Python, not the model.

  5. And what about Moga? → Which of those two is worse? · 4s each

    Show: it carries the conversation, and the second question compares Bathinda and Moga — not all 23.

    Say: this is what makes it a conversation rather than a search box.

  6. Is the water in Bathinda safe to drink? · 12s

    Show: the badge flips to CGWB report and the citation becomes a page number.

    Say: the database holds no water quality data at all, so this comes from the report instead. Use the slow moment to explain that numbers never go through the document search — retrieving prose about a figure loses the station and the date.

  7. What's the groundwater status in Mumbai? · 1s

    Show: a refusal that names its actual scope.

    Say: it would rather say no than guess.

What judges will ask

Answer with the specific story, not the general claim. Specifics are what make it sound built rather than described.

"How do you know it isn't hallucinating?"

The strongest answer we have: during testing, the model produced an answer citing Kot Shamir — a Bathinda station — as the source for a Ludhiana figure. Our LLM verifier approved it. That's exactly why verification isn't left to a model. Eight plain-Python checks test every citation, figure, district, year and unit against the retrieved data before anything is shown.

"Isn't this just a wrapper around an LLM?"

Three of the five agents involve no model at all. Retrieval is a dictionary lookup and SQL, the projection is numpy, and the verification is plain Python. The model understands the question and writes the sentence. It never supplies a number.

"Why a small local model instead of GPT-4?"

Deliberate. It runs fully offline — no internet, no API key, no cost — which also means it can't fail on venue wifi. And it's the stronger claim: the guarantees come from the checks, not from the model being good. One line in the config switches it to Claude if anyone wants to see that.

"Where did the risk categories come from — did you make them up?"

CGWB categorises blocks, never districts, so a district category can't be transcribed — it has to be derived. Ours is the category held by most of the district's blocks, ties broken toward the worse one, and the block counts are stored alongside so an answer can show its working. We cross-checked the extraction against a second table in the same report, which caught four wrong categories on the first attempt.

"What happens when it gets something wrong?"

It shows the raw data and says it couldn't verify the wording, rather than showing a confident sentence. An unverifiable answer is never presented as if it were verified.

"Is the data live?"

No, and don't imply otherwise. It's CGWB's published monitoring data through 2024, loaded into Postgres. CGWB publishes quarterly, not live.

"Why isn't it deployed?"

The network we built on blocks every database port, so the managed database was unreachable during development. Running locally was the lower-risk choice for demo day too — venue wifi usually has the same restrictions. Nothing about the architecture prevents deploying it.

"What doesn't it do?"

Answer this one straight — see below. Being able to name your own limits is worth more than pretending there aren't any.

Do not claim these

A judge who catches one overclaim will discount everything else you said. All of these are things it would be easy to imply by accident.

Not true, don't say it

  • "Real-time data." It's published CGWB data through 2024.
  • "Works for all of India." Punjab only — 23 districts. It refuses anything else, and that refusal is a feature worth showing.
  • "It predicts when the water will run out." It projects a straight line at the measured rate and says explicitly that it assumes the rate holds and ignores policy, rainfall and aquifer behaviour. Call it an order of magnitude, not a forecast.
  • "CGWB says 30 m is critical." CGWB publishes no depth threshold at all. 30 m is our stated pumping limit. The system itself is careful about this — don't be less careful than it is.
  • "It's never wrong." It's checked. Those are different claims, and the second one is the impressive one anyway.
  • "Machine learning model." The trend fitting is a straight-line fit. Don't dress it up.

Known weaknesses — own them first

If you raise these before a judge does, they read as self-awareness. If a judge raises them first, they read as gaps.

WeaknessWhat to say
One user at a timeOne model on one machine. Two questions at once and it crawls. A queue is the obvious fix; we didn't need it for a single-user demo.
Plain proseA 7B model writes plainly. That's the cost of the offline decision, and we took it knowingly.
One documentSemantic search covers one CGWB report. Anything outside it has no source, and it says so rather than guessing.
Map needs internetOnly the map tiles. Everything else runs offline.
No multi-hop questions"Compare the trend in the three worst districts" is beyond it.
Not deployedNetwork constraints during development; runs locally by design.

Roles for the slot

Decide these before you walk up, not at the laptop.

RoleJob
DriverTypes the questions, one at a time, in the script order. Doesn't talk while typing. Never types while an answer is running.
NarratorDoes the talking. Reads one progress line aloud per question. Owns the Kot Shamir story.
BackupWatches the health dot. Knows the restart commands. Takes hostile questions so the narrator keeps the thread.

Everyone should be able to answer "how do you know it isn't hallucinating?" — that question will come, and it's the one the whole project answers.
